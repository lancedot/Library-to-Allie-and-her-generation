# 第二章：把重复变成基础设施

> 读完这章，你会明白如何把财务部门的手工重复操作，一步一步变成 AI 可以调用的标准化能力。

---

## 从一个真实的烦恼开始

财务部门有一类工作，每个人都做过，每个人都烦过：

定时去系统里导报表。

每个月固定时间，登进去，点几下，等它生成，下载，改文件名，放到对应的文件夹。如果管的主体多，这件事要做十几遍。有时候系统卡，有时候忘了，有时候导出来的格式不对还要手动处理。

这件事本身没有任何业务价值，但它每个月都必须发生，而且必须由人来做——或者说，过去必须由人来做。

这类工作，就是我们要改造的第一类目标。

---

## 识别"待封装的能力"

财务部门的重复操作，大概可以分三类：

**第一类：从外部系统抓数据**

税务局网站的发票信息、海关数据、监管报送平台的状态——这些数据存在于各种政府或第三方系统里，没有 API，只能人工登录操作。

这类任务的特点：步骤固定，判断少，频率高，但需要人守着。

**第二类：从内部系统导报表**

财务系统里的各类报表，按月、按季、按需导出。如果系统没有批量导出功能，或者无法直接连数据库，管理主体一多，就是大量重复点击。

这类任务的特点：完全可以描述清楚每一步，没有任何需要人判断的地方。

**第三类：从数仓取数**

如果已经有数据仓库，这类任务最接近标准化——本质上是把 SQL 查询封装好，按需触发，结果输出到指定位置。

这三类任务，有一个共同特征：**它们现在消耗人的时间，但人在这个过程里没有贡献任何判断力。**

这就是"待封装的能力"的识别标准——**不需要人判断，只需要人执行的任务，都是待封装的能力。**

---

## 第一步：用 RPA 固化重复操作

识别出目标之后，第一步是把这些操作固化成可以自动运行的脚本。

这就是 RPA（Robotic Process Automation，机器人流程自动化）的用武之地。

RPA 的本质：**用软件模拟人的操作——打开浏览器、点击按钮、填写表单、下载文件——然后把这个过程录制下来，自动重复执行。**

### 用 Codex / Claude Code 写 RPA 脚本

过去，写 RPA 脚本需要专业的开发人员。2026年，这件事已经可以用 Coding Agent 来做。

**实际流程：**

1. 把你要自动化的操作描述清楚：目标网站或系统、操作步骤、需要抓取或下载的内容、存储位置
2. 把这些描述输入 Codex 或 Claude Code，让它生成脚本
3. 在测试环境里运行，检查结果，告诉 Coding Agent 哪里不对
4. 迭代修改，直到脚本稳定运行

**以税务局发票数据为例，你给 Codex 的描述大概是这样的：**

```
帮我写一个 Python 脚本，实现以下操作：
1. 打开[税务局网站]，用账号密码登录
2. 进入"发票查询"页面，按月份筛选上个月的数据
3. 下载查询结果为 Excel 文件
4. 把文件重命名为"发票数据_YYYYMM.xlsx"，保存到指定路径
5. 如果下载失败，发送一条错误通知

登录信息和路径通过配置文件读取，不要硬编码在脚本里。
```

这个描述，Codex 能给你一个可以运行的初版脚本。你在测试中发现问题，继续在对话里告诉它，迭代修改。

**重要提醒：** 脚本里涉及账号密码的部分，不要直接写进代码——通过配置文件或环境变量管理。这是基本的安全实践。

### 两种 RPA 路径

从实际操作经验来看，RPA 脚本有两条路：

**API 路径（优先选择）：** 如果目标系统有 API，通过 API 取数是最稳定的方式。系统界面变了不影响脚本，速度快，错误处理也更干净。

**网页巡检路径（系统没有 API 时的替代方案）：** 用脚本模拟浏览器操作。这条路有一个固有风险：目标网站的界面一旦更新，脚本可能就失效了，需要维护。把它理解成"过渡方案"，等目标系统开放 API 之后，迁移过去。

---

## 第二步：用 MCP 把 RPA 变成 AI 可调用的工具

RPA 脚本跑通之后，它还只是一个"定时自动执行的程序"——员工需要手动触发，或者等定时任务自动运行。

下一步，是把这些脚本封装成 AI 可以调用的工具。

这就是 **MCP（Model Context Protocol）** 的作用。

**MCP 是什么：** 一个开放协议，让 AI 模型可以标准化地调用外部工具和数据源。把你的 RPA 脚本封装成 MCP 服务之后，AI Agent 就可以像调用一个函数一样，触发这个脚本的执行。

**封装之后发生了什么：**

员工不再需要知道脚本在哪里、怎么运行。他们只需要告诉 AI："把上个月的发票数据下载下来放到公盘"——AI 调用 MCP 服务，触发脚本，脚本执行，文件出现在公盘。

从"员工手动操作系统"，变成了"员工向 AI 下达指令，AI 调用工具完成操作"。

**除了 RPA 封装，还可以封装什么：**

- **财务信息查询：** 把财务系统里常用的查询封装成 MCP 服务。员工问"这个供应商今年的应付账款余额是多少"，AI 直接查系统返回结果，而不是让员工自己登系统查
- **数仓取数：** 把常用的 SQL 查询封装好，按参数触发，结果直接返回给 AI
- **文件操作：** 从公盘读取、写入、整理文件，成为 AI 工作流里的标准动作

## 第三步：双入口设计

工具封装好之后，需要考虑一个实际问题：**不同成熟度的员工，怎么用这套工具？**

有的员工习惯用 AI，有的员工不习惯，有的员工处于过渡阶段。如果只有一个入口——比如只能通过 Agent 调用——不习惯的员工就用不起来。

解决方案是**双入口设计**：

**入口一：网页界面（人类友好入口）**

做一个简单的网页界面，把常用操作做成按钮或表单。员工点击"导出上月报表"，后台触发对应的工具，结果送到公盘。

这个入口，完全不需要员工了解 AI 或 Agent，只要会点击就能用。

**入口二：Agent 入口（AI 原生入口）**

通过 Agent，员工用自然语言下达指令，Agent 判断意图，调用对应的 MCP 工具完成任务。

这个入口，适合已经习惯和 AI 交互的员工，或者需要组合多个操作的复杂指令。

**两个入口的关键：** 它们调用的是同一套工具，只是触发方式不同。基础设施只需要建一次，两个入口共享。

这个设计解决了一个组织转型中的真实矛盾：**你不能等所有人都准备好了再开始，但你也不能强迫所有人同时切换。** 双入口让不同进度的人都能用起来，而不是只有"先进"的那部分人在受益。

## RPA 的三个原则：不只是点得快

很多人把 RPA 理解成"让机器点得更快"。

在简单场景里这没有问题。但在财务这个高风险场景里，**自动化最重要的不是速度，而是可信**。

一个可信的 RPA，需要满足三条原则：

**原则一：要记录**

每一个自动化动作，都要留下证据。

脚本运行了，下载了什么文件，存到了哪里，有没有报错——这些都要有日志记录。最好还有关键步骤的截图或状态变化记录。

原因很简单：财务场景出了问题，你需要能说清楚"脚本在这一步做了什么"，而不是"我以为它跑成功了"。

**原则二：要暂停**

不是所有步骤都适合一口气跑到底。

涉及提交、不可逆操作的节点，脚本应该在这里停下来，等人确认之后再继续。这不是因为 AI 不可信，而是因为这类操作本身就需要人的最终授权——自动化不改变这个事实。

**原则三：要承认边界**

RPA 能做的是：按固定步骤操作界面、下载文件、填写表单。

RPA 做不到的是：理解操作背后的业务逻辑、判断结果是否合理、在系统报错时知道该怎么办。

能点按钮，不等于理解后台业务规则。这个边界要在脚本设计阶段就明确——哪些情况应该停下来让人处理，而不是靠脚本自己猜。

一句话总结：**好的 RPA 是"带证据的重复劳动接力"——机器做重复动作，人保留关键判断。**

---

## 整条路的全貌

把三个步骤放在一起，这条路的全貌是：

```
手工重复操作
    ↓ 识别"不需要人判断的任务"
RPA 脚本（用 Codex / Claude Code 生成）
    ↓ 稳定运行后封装
MCP 工具（AI 可以调用的标准化接口）
    ↓ 部署双入口
网页入口  +  Agent 入口
    ↓ 员工使用
人只负责下指令和验证结果
```

走完这条路，原来需要人手动做的那些重复操作，变成了基础设施——可以随时被调用，不依赖某个人记得去做，也不需要某个人守在那里等它跑完。

---

## 一个需要说清楚的期望管理

这条路不是一蹴而就的。

**RPA 脚本需要维护。** 目标系统更新了界面，脚本可能失效。特别是网页巡检类的脚本，维护成本比 API 调用高得多。把维护时间算进去，才是真实的投入产出。

**MCP 封装需要一定技术基础。** 不是说员工自己做不到，但需要有人（可能是你自己，可能是技术同事，可能是 Coding Agent）来负责封装和维护这层。

**双入口的网页界面需要开发。** 好消息是，Codex 可以帮你做这件事，不需要专业前端开发人员。坏消息是，它仍然需要时间和迭代。

把这些成本如实估进去，这条路仍然是值得走的——因为一旦基础设施搭好，它带来的效率提升是持续的，不是一次性的。

## 📌 本章要点卡

1. 识别待封装能力的标准：**不需要人判断、只需要人执行的任务**——这类任务都是候选
2. 三步路径：**RPA固化 → MCP封装 → 双入口部署**——每一步都有独立价值，不需要一次全部到位
3. 双入口解决真实矛盾：**不同成熟度的员工可以共存**，基础设施只建一次，两个入口共享
