# 第 1 章：面向 2026 年重启的创业生命周期

AI 正在重塑创业公司被搭建起来的方式。今天，从未写过一行代码的创始人也能发布生产级应用；而精简到 10 人的独角兽，已经不再只是一个草根逆袭故事，而是一套可以被主动设计的行动方案。

到 2026 年，AI 已经能够编写生产级代码、开展市场研究、综合竞争格局、起草投资人材料，并自动化运营工作流。过去，即使是经验丰富的技术型创始人，也要跨过陡峭的学习曲线，才能把工具、平台和系统整合起来，让一个想法真正落地。AI 首先消除了这道门槛，让「谁可以创办公司、谁可以做出产品」这件事变得更加平等。

在 2026 年，一个好想法能把创始人带得比以往更远。智能体式编程把过去需要一支工程团队完成的工作，压缩成创始人自己就能交付的成果。

传统的创业增长路径默认了一条弧线：验证 -> 融资 -> 招人 -> 构建 -> 再融资 -> 增长 -> 再招人 -> 循环往复。如今，AI 已经打破了一个旧预期：创业生命周期中的每一个新阶段，都必须对应更大的团队、不同的技能组合，以及新一轮融资。

这本手册会按照这些新现实，重新绘制创业旅程的四个核心阶段：想法、MVP、发布和规模化。我们会考察，当 AI 成为技术建设和组织建设的核心时，每个阶段会呈现什么样子；每个阶段适合使用哪些工具；以及创始人如何借助这些工具压缩时间线。如果你已经准备好寻找从想法到退出之间最短的路径，请继续读下去。

# 第 2 章：创始人的含义正在改变

过去，创始人常常由「他们能做什么」来定义：技术型创始人写代码，非技术型创始人负责业务运营和成交。但到 2026 年，创始人可以使用的模型、系统和 AI 智能体，已经拆掉了「能构建的人」和「拥有值得构建的想法的人」之间那堵墙。

AI 原生创业公司正在从根本上改变「成为创始人」意味着什么。如今，一个没有工程背景的人，也可以构建生产级软件，把自己的想法变成现实；而一个技术能力很强、却缺少商业知识的创始人，也能轻松产出一套上市策略、财务模型，以及高度打磨过的融资演示文稿。

从历史上看，创始人大部分时间都花在执行模式里：写代码、管人、处理日常运营工作。在 AI 原生创业公司里，创始人的角色会少一些个人贡献者属性，多很多「智能体编排者」属性。这些智能体是专门化的 AI 助手，可以读取文件、运行命令、执行代码，甚至浏览网页。创始人的注意力会向上移动，转向更高阶的工作：产生想法，并指挥那些负责把想法落实的系统，包括 AI 智能体、工具，以及可能存在的小团队。

不过，把 AI 作为核心基础设施所带来的最革命性结果，是它释放了拥有领域专业知识的非技术型创始人。当创始人群体不再局限于工程背景的人，你就会看到由完全不同生活经验的人建立的创业公司。他们解决的是真实问题，而这些问题过去可能从未被传统技术创始人路径优先考虑，甚至根本没有被看见。

## 精简创业公司的 AI 工具能力

传统创业模式默认你需要雇工程师来构建产品，雇销售人员来卖产品，再雇运营人员来维持公司运转。团队人数被视为组织动能和产品成熟度的象征。

2026 年的早期创业公司已经大不一样。它们在设计上就极其精简，常常只有创始人一个人，或者再加上寥寥几位伙伴。通过把 AI 作为技术建设和组织建设的基础设施，这些公司可以在扩大团队之前，就完成产品验证、获得早期收入，甚至实现盈利。AI 尤其在三个方面，让一家创业公司能够像规模大得多的组织一样运转：研究、智能体式编程，以及关键业务运营的工作流自动化。

## 对话式智能与研究

### 可以理解为：每个领域的随叫随到专家

想想创始人在第一年需要知道多少事情，而这些事情他们在出发时几乎肯定并不了解：我该如何设置薪资发放？我该如何规划产品开发冲刺？我该如何写出一份紧凑有力的投资人备忘录？

过去，这类早期创业问题通常只有同一个答案：去找懂的人。对于自力更生或尚处于种子轮前的创始人来说，这可能意味着把本该用于构建的时间耗在搜集知识上，或者不得不烧掉一部分早期资金去请顾问。现在，他们拥有了 AI：一个横跨几乎所有可想象领域的随叫随到专家。

- 深度研究：竞争分析、市场规模测算、财务建模
- 文档起草：融资演示文稿、案例研究、投资人备忘录、PRD
- 战略思考伙伴：反方论证、预演式复盘、情景规划、路线图优化

## 智能体式编程

### 可以理解为：永远在线、不会被卡住的工程师

过去，构建软件通常意味着你需要一位技术联合创始人、一家外包开发公司，或者足够长的资金跑道，让你能在写出第一行生产代码之前先招起一支工程团队。

现在，智能体式编程工具让每一位有创业想法的人，都可以用自然语言描述自己想构建什么，并指挥 AI 生成、测试、调试和重构一个生产级代码库，其速度和规模接近一整支工程团队。从「我有一个想法」到「我有一个产品」之间的时间线已经被压缩。创始人的角色也因此更集中在「构建什么」以及「为什么构建」上，而 AI 负责搭建真实可用、面向真实用户的基础设施。

## 工作流自动化

### 可以理解为：按需调用的自动化运营团队

即使创始人已经能像顾问一样研究、像工程团队一样构建，仍然有一整类工作既不属于战略规划，也不属于产品开发，却必须有人完成。日程安排、更新 CRM、拉取周报、保持文档最新、发布内容、跟踪合规要求、管理公司运行所依赖的各种工具和系统之间的连接组织，这些也都必须发生。在一家精简创业公司里，这些负担主要会落到创始人身上，而它会显著消耗本应投入高阶决策的时间和注意力。

AI 工具驱动的工作流自动化，可以卸下这部分负担。重复性的运营任务可以被配置为自动发生：当交易阶段推进时，CRM 自动更新；周报自动汇总；产品文档随着产品变更同步更新。更关键的是，Claude Cowork 可以接入创业公司运行所依赖的互联系统，包括你的项目管理工具、沟通工具栈和数据来源，而不需要有人专门构建并维护这些集成。在「Day Zero」创业公司里，这个「有人」几乎总是创始人自己。

## 时机与编排决定一切

能够有效驾驭 AI 研究、自动化和智能体式编程能力的创始人，可以建立一家杠杆远高于团队人数所暗示规模的创业公司。他们也能把大部分时间和带宽投入真正重要的工作。

但这些工作不会自动驾驶。负责编排这些 AI 工具的创始人，必须知道如何使用它们，以及何时使用它们。本手册接下来的部分，将继续探讨创始人在沿着 AI 原生创业路径前进时会遇到的目标和挑战，以及如何在旅程的每个阶段有效应用 AI 工具。

# 第 3 章：想法阶段

每一位创业者的起点都一样：有一个问题让他们怎么也放不下。想法阶段，就是想法第一次碰到现实的地方。到了 2026 年，创业成功需要一种克制：在证据足以支撑之前，不要急着动手构建。

这一阶段的工作包括研究、客户发现、竞品分析，以及诚实地评估那些可能推翻你想法的证据。所有这些，都应该发生在你让 Claude Code 生成第一行生产代码之前。

## 想法阶段的目标

在想法阶段，创始人的主要目标是以研究为导向的验证：在投入资源开始构建之前，先拿到扎实证据，证明一个真实问题确实存在，并且你提出的解决方案能够有效解决它。

更实际地说，想法阶段是一组创始人必须大致按顺序回答的问题：

- 这个问题真实吗？是否足够具体、足够频繁，值得围绕它建立产品？
- 到底是谁遇到了这个问题？这些人能否构成一个市场？
- 是否已经有人在解决它？如果有，他们怎么解决，解决得如何？
- 一个真正能解决这个问题的方案到底需要做什么？我的想法是否做到了？

这些问题的答案最终会汇总成一个终极问题：这件事值得做吗？

这意味着，在开始行动之前，你需要先变得具体。“人们在报销上很痛苦”只是一个观察。“中型企业的财务经理每周要花 4 小时以上核对报销提交，因为他们现有的工具无法和会计软件集成”，才是一个可以被检验的假设。

## 想法阶段的退出标准

想法阶段的退出条件，是找到问题-解决方案匹配。也就是说，在开始构建真正解决问题的东西之前，你已经主要通过真实的人类对话获得了定性证据，证明你是在为真实的人解决真实的问题。

当你可以对下面三个问题都回答“是”时，就可以离开想法阶段：

1. **这个问题真实吗？是否足够具体？** 肯定回答这个问题，意味着你能够准确说出谁在经历这个问题，他们多频繁遇到，它对他们造成多严重的影响，以及他们现在如何处理。
2. **你的解决方案是否解决了真正的问题？** 不是你一开始假设的那个问题，而是验证过程揭示出来的问题。有时候二者相同，但并不总是如此。
3. **你是否有足够信号，值得开始构建？** 在这个阶段你永远不会拥有确定性，等待确定性本身就是一种失败模式。但你需要足够的定性证据，能说明投入 MVP 是一个经过推理的决定，而不是一次信仰跳跃。

## 想法阶段的挑战

想法阶段是整个创业旅程中最重要的工作发生之处，因为最具后果性的错误也往往在这里出现：此时犯错，很快就可能让一个刚萌芽的项目偏离轨道。

不过，想法阶段的大多数挑战，本质上都来自行动速度超过了理解深度。因此，那些能带着思考和审慎向前推进的创始人，通常会稳步取得进展。

### 把构建误认为验证

**挑战：** 当技术障碍被移除时，一个充满热情的创始人很容易跳过创业旅程中最重要的工作：验证自己的想法是否真的是人们需要并愿意使用的解决方案。

即使在当前的智能体式编程时代到来之前，也有 42% 的创业公司因为做出了没人想要的东西而失败。现在，Claude Code 这类智能体式编程方案极大压缩了“我有一个想法”和“我有一个产品”之间的距离，这个失败率只会继续上升。

对于拥有一个足以震动神经元的好点子的创始人来说，从来没有比现在更好的时代。但反过来，快速、轻松地搭出一个看起来像产品的原型，也给 AI 原生创业公司带来了真正危险的生存风险。

直到不久前，构建仍然需要真实的开发时间和预算。哪怕只是做出一个基础原型，通常也需要几个月。如今，技术开发的门槛大体消失，AI 让创始人太容易绕过现实世界的效用验证，直接开始构建。

要达到问题-解决方案匹配，正确顺序是先验证假设，再开始构建。但很多第一次创业，甚至有经验的创始人，会误以为 AI 可以绕过这一要求，把流程变成：有一个想法 -> 立刻做出原型 -> 把原型的存在本身当成验证。原型成了相信最初假设正确的理由，而假设本身从未被真正检验。

一个可运行的原型，很容易被误认为是你正在解决真实问题的具体证据。但它并不是。你的原型更像是一个有用的压力测试道具，用来和潜在用户展开对话。真正的证据，是这些对话本身。

### 过早扩张

**挑战：** 当构建变得轻松且即时，你可能会把执行规模扩张到远远超过业务需求的程度。

过早扩张，意味着在真正验证某条产品路径值得投入之前，就已经对它做出承诺。

这一直是创业公司的杀手。但 AI 让创始人更容易在毫无察觉的情况下掉进过早扩张的陷阱。智能体式编程助手非常强大，以至于你很容易在尚未验证问题-解决方案匹配之前，就把执行推进得过远，而且过程中甚至没有意识到自己已经偏航。

它会围绕一个根本有缺陷的前提生成、测试、调试和重构代码库，而且热情丝毫不亚于面对一个绝佳想法。系统中的智能来自你。这个阶段的首要指令，是让你的理解和判断始终跑在构建前面，尤其是在构建如此快速、感觉如此轻松的时候。

### 失去客观性

**挑战：** 如果你让 AI 工具为你已经相信的事情寻找证据，它会找到。确认偏误如今自带研究引擎。

确认偏误一直是创业中的职业风险：创始人天然会对自己的想法充满热情。现在，AI 工具让确认偏误显著增强。让 AI 验证你的创业想法，它会找到支持证据；让它估算你的潜在市场，它会找到一个让你的 TAM 看起来足以融资的数字。

AI 会跟随你的方向。这意味着，如果创始人没有提出艰难问题，就可以比以往任何时候都更快地为一个糟糕想法搭建出一套精致、看似研究充分的论证，同时还会自信地认为自己确实完成了尽职调查。解药仍然是同一个工具，只是要把它指向相反方向：AI 可以像验证一个想法那样彻底地压力测试它。

当研究和结构化的对抗性思考暴露出你的想法需要修正的证据时，这就是转向的信号。

## Claude 如何帮助想法阶段的创始人

推动一个 AI 原生创业概念穿过想法阶段，可能会让人觉得漫长无比。你是创始人，你只是想赶紧构建。但这个至关重要的起步阶段，本质上是研究和验证练习。这意味着，在全力写代码之前，你应该先使用那些能帮助你更严谨思考的工具。

下面是如何在 Claude 的不同产品形态中，包括 Chat、Claude Cowork 和 Claude Code，尽可能快速但又负责任地完成想法阶段的尽职调查。

### Chat、Claude Cowork 还是 Claude Code：选择合适的 Claude 界面

AI 让创业者更容易快速发布、自动化繁琐工作流，并以更大规模运转。但你使用的界面很重要。根据手头任务的不同，Chat、Claude Cowork 和 Claude Code 各有适用场景。

**Chat** 适合在不离开当前应用的情况下进行快速交流。用它处理运营公司时不断出现的小任务：从厚重的投资人备忘录里提炼一句话结论，在董事会会议前快速校验一个说法，或者理清团队里一条很长的 Slack 讨论。

**Claude Cowork** 适合真正需要时间的知识工作：从多个来源提取信息、理解它们，并产出完成度较高的文档、演示或电子表格。比如，把一整个文件夹的客户访谈记录整理成下一次产品评审用的主题发现文档；在融资前，从十几个供应商网站构建竞品格局；或者设置一个每周一早上的固定任务，从已连接的工具中拉取指标，并把每周 KPI 简报放进共享文件夹。

**Claude Code** 是给团队工程师使用的智能体式编程环境：它可以直接访问代码库，支持 Plan Mode、git 集成，以及本地、IDE 或沙箱云环境。精干团队可以在这里围绕不断增长的代码库发布功能，迁移 MVP 时代留下的遗留代码，并在不等待新增人手的情况下，从原型走向生产。

| 如果任务是…… | 选择 | 原因 |
| --- | --- | --- |
| 一个问题、一次改写、一次快速头脑风暴 | Chat | 快速、对话式、无需设置 |
| 基于你的文件和系统做研究、分析或产出完成文档 | Claude Cowork | 文件夹访问、连接器、技能、计划任务 |
| 编写、测试或发布软件 | Claude Code | 代码库访问、diff、git、开发环境 |

三者底层使用的是同一个 Claude；变化的是它周围的工作空间。

### 定义并压力测试问题假设

你自己的领域经验和前期研究，已经形成了一个假设。第一项工作，是把它打磨到真正可以被检验。Claude 在这里尤其有用，因为它会逼迫你变得具体：到底是谁遇到这个问题？频率如何？严重程度如何？他们现在怎么处理？一个无法精确回答这些问题的问题陈述，还没有准备好接受验证。

- **练习：** 和 Claude 一起打磨你的问题陈述，直到它成为一个可检验的假设。例如，“合同审查太慢”并不具备真正可检验性。但“中型企业的内部法务团队每个合同审查周期要花 3 天以上，因为红线修改分散在邮件线程中，而不是在单一的版本控制文档中管理”，就非常可检验。

下一步，是让 Claude 反驳你的想法，并寻找能够推翻你假设的证据。这可能会暴露负面的市场信号、失败的竞争对手、客户行为模式，以及那些支持性综合分析会悄悄降权的结构性障碍。

目标是在进入客户发现之前，就已经用当前最强的反方论据压力测试过自己的假设。这样一来，信息性用户访谈才会真正保持开放，而不是变成寻找确认的过程。

> 注：把 Claude 当作结构化的“唱反调者”，是 AI 创业生命周期每个阶段的核心用法。

### 市场研究与竞品格局绘制

#### 评估竞争对手

创业公司中有一种特定现象叫作“忽视竞争对手”：创始人过度聚焦于自己的愿景和执行，以至于系统性低估同一领域里其他人在做什么。幸运的是，AI 提供了解药：让 Claude 给出最有说服力的论证，说明为什么这个解决方案空间里的某个竞争对手会成功，而你不会。

Claude 可以分析为什么他们的方法实际上更好，为什么客户会选择他们，以及为什么你认为的潜在差异化未必像你想象的那样牢固。

- **练习：** 让 Claude 按层级绘制你的竞品格局：直接竞争对手、间接竞争对手、潜在收购方，以及可能进入你所在空间的相邻玩家。然后让它说明每一层为什么都对你的成功构成真正威胁，而不只是指出那些最容易被你驳倒的威胁版本。

#### 市场研究

Claude Code 可以综合公开可得的客户反馈，找出反复出现的抱怨和未被满足的需求。额外好处是：这基本上是在免费研究竞争对手的客户。

- **练习：** 指示 Claude Cowork 综合你关键来源中的竞品评论，识别出现有解决方案尚未解决的主要抱怨。如果你的假设解决了其中一个或多个问题，那就是问题-解决方案匹配的强证据。如果没有，这同样值得知道。

Claude Cowork 还可以从密集的行业报告、分析师文件和市场研究文档中提取相关信息和数字。随后，这些经过清理和综合的输入，会成为 Claude 分析工作的理想上下文。

- **练习：** 基于公开数据建立 TAM/SAM/SOM 模型，并压力测试其背后的假设。识别市场是在扩张、整合，还是已经成熟；这种背景会影响你对时机和差异化的判断。绘制买方格局：谁掌握预算，谁影响决策，这两者是否是同一个人。

#### 趋势分析

最后，用 Claude 倾听早期指标，判断你是否是在合适的时点进入市场。跟踪那些已经在讨论你所关注问题的 subreddit 和 LinkedIn 群组，观察用户描述痛点时使用的准确语言。让 Claude 识别类似市场中曾经被解决的相似问题，并提取哪些做法有效、哪些无效。找出可能加速或威胁这个机会的监管、技术或人口结构趋势。

- **练习：** 让 Claude 识别三个外部趋势，可能是监管、技术或人口结构层面的趋势，它们可能在未来两年显著影响你的市场。然后评估每个趋势对你的具体假设来说是顺风还是逆风。

> 注：本节中的市场研究和竞品绘制不是一次性练习。你会在 MVP 和发布阶段继续获得新发现，并不断演化自己的思考。因此，只要你的假设发生变化，就应该重复这些练习。

### 规划并设计客户发现

你通过和潜在用户交谈所能学到多少，取决于两件事：（1）你提出的问题质量如何；（2）你是否把这些问题问给了正确的人。Claude 尤其适合帮助开展客户发现，包括该和谁聊、该问什么，以及如何理解你听到的内容。

#### 应该和谁聊

一个精确的目标画像，远比一长串联系人更有价值。它应该包括最有可能强烈感受到该问题的具体职位、公司类型、团队结构和资历层级。然后，再识别这些人实际在哪里可以被触达：他们聚集的社区、活动、LinkedIn 群组和 Slack 工作区。基于他们与问题的接近程度，建立优先联系框架，决定先联系谁。

#### 应该问什么

目标确定之后，使用 Claude 搭建访谈框架本身：正确的问题、正确的顺序，并且结构要能让人说出自己实际做了什么，而不是他们以为自己将来会怎么做。新手创始人的常见错误，是提出一个关于未来的泛泛开放问题，比如“你会使用这样的东西吗？”，而不是具体询问相关的过去经历：“请讲讲你上一次处理这个问题是什么情况。”

Claude 也可以指出你草拟的问题中，哪些在引导受访者，哪些过于宽泛，哪些可能产生噪音而不是信号。Claude 还可以帮助你设计追问，用来处理回避，或者深入挖掘重要问题上含糊的回答。

如果你的假设涉及不止一种角色，Claude 还可以为每种角色设计不同的问题集。财务经理和 CFO 面对同一个问题时关系并不相同，单一访谈框架会抹平这种差异。

- **练习：** 先手写你的访谈问题，再让 Claude 审核。明确要求它标出任何带有引导性、面向未来、过于宽泛，或者更容易产生社会期望答案而非诚实回答的问题。然后让它为访谈中最可能出现回避的两三个时刻，建议后续追问。

#### 访谈后分析

每次对话结束后，用 Claude 做复盘：把你的笔记喂给它，让它识别哪些内容确认了你的假设，哪些内容挑战了假设，哪些内容真正出乎意料。等你积累了一批访谈后，把完整访谈笔记交给 Claude Cowork，让它找出反复出现的主题、矛盾之处，以及正反两个方向上最强的信号。然后，把综合输出再带回 Claude，让它指出你对数据的解读中，哪里可能是在用自己想听到的内容做模式匹配，而不是在看实际存在的东西。

- **练习：** 每完成五次访谈，就指示 Claude Cowork 综合你的笔记，并产出两张清单：支持你假设的证据，以及挑战你假设的证据。如果第一张清单明显长于第二张，就问 Claude：这种不对称反映的是数据本身，还是你原本希望找到的东西？

#### 客户触达与排期

使用 Claude Cowork 自动化围绕建立联系人名单、开展触达和安排用户访谈的运营工作。

Claude Cowork 可以使用你和 Claude 一起定义的目标画像，包括职位、公司类型和资历层级，来研究并整理结构化的潜在客户名单和已验证联系方式。随后，它可以批量撰写个性化触达邮件，并根据每个人的角色和背景进行定制。

随着回复到来，它可以通过 MCP 连接 Gmail 和 Google Calendar 来管理邮件线程，处理排期请求，并把访谈加入日历。这个工作流还会继续：Claude Cowork 按照设定节奏生成跟进草稿，例如给 7 天未回复的联系人发送跟进，并在每一步完成时更新你的跟踪表，让你始终知道每个潜在客户在管道中的状态。

- **练习：** 把经过验证的访谈目标画像交给 Claude Cowork，让它建立潜在客户名单，起草个性化触达序列，并设置一个跟踪表，其中包含触达状态、跟进节奏和访谈完成情况等列。然后让它负责协调工作，你则专注准备真正的对话。

### 设计最终解决方案概念

你已经完成了验证工作：问题是真实的，你知道谁遇到了它，并且有一个证据支持的解决方案概念。使用 Claude 从各个角度发展并挑战你的解决方案概念：缺口在哪里？有哪些替代方案？如果这个方案要在规模化时成立，哪些事情必须为真？

这是一个重要的现实检查点：这个设计是否真的解决了验证过程揭示出来的问题，而不是你一开始假设的问题？

- **练习：** 把你的解决方案概念展示给 Claude，让它识别你的设计最依赖的三个假设。然后问它：每个假设要成立，必须满足什么条件？如果其中任何一个不成立，会产生什么后果？

### 用 Claude Code 构建轻量原型

现在来到有趣的部分：有了经过验证的假设和经过压力测试的解决方案概念，你终于可以开始构建一些东西了。

这是想法阶段中 Claude Code 登场的时刻。即使你之前一直在试做小东西，现在才是生成正式轻量原型的节点：只做出把你的想法放到真实人类面前、获得真实反应所需的最小表面积。

你还不是在构建现实世界中的完整产品，至少现在还不是。你是在构造一个功能性样本，用于客户和投资人对话。真实用户对一个他们真的能触摸和试用的东西做出的反应，会告诉你许多十几次问题-解决方案发现访谈无法揭示的事情。此前，你是在确认自己要解决的问题真实存在；现在，你是在邀请潜在用户与拟议解决方案互动。

- **练习：** 定义你的解决方案所依赖的单一核心交互。指示 Claude Code 只构建这一点。当你拿到它之后，把它放到五个来自已验证目标画像的人面前，请他们试用。你从这五次对话中学到的东西，将决定你是继续构建，还是回到画板前重新思考。

到达想法阶段的终点，是 AI 创业竞赛中的巨大跃迁。因为此时你不再是在押注直觉，而是在基于证据执行。

接下来进入 MVP 阶段。创始人的指导问题将从“这件事值得做吗？”转变为“我们最先到底应该构建什么？”，而 AI 的主要角色也会从研究伙伴转变为施工队。

# 第 4 章：MVP 阶段

很多创始人把 MVP 阶段视为一个建设阶段，但 MVP 阶段本质上仍然是一个收集证据的过程。不同之处在于，你现在收集的是关于解决方案的证据，而不是关于问题空间的证据。更具体地说，是一个真实、可识别的用户群体是否认为它有足够价值，愿意使用它、再次回来、为它付费，和/或把它告诉别人。

## MVP 阶段的目标

作为 AI 原生创业公司的创始人，你的目标是把一个经过验证的问题，转化为真实用户确实会使用的可运行产品。这不是包含所有路线图功能的完整版本，而是你想法中最小、最聚焦的一次迭代：它把一个真实解决方案放到真实用户面前，并生成关于产品-市场匹配的真实证据。

与此同时，你现在的构建方式会决定之后什么是可能的。这意味着，MVP 阶段还有第二个同等重要的目标：快速前进，但不要积累那种会复利增长的技术债。否则，一旦真实用户以有意义的数量到来，它就会立刻回来缠住你。

最后，从第一天起就投资于持久上下文，才能让 AI 成为力量倍增器，而不是熵的来源。在 AI 原生创业公司中，代码库是你一轮又一轮和 AI 协作的对象，因此可读性是基础。那些跳过规格说明、架构决策和上下文文件（例如 CLAUDE.md）的创始人，会撞上一堵可预期的墙：每个新会话都需要重新解释代码库，AI 生成的修改也会逐渐偏离最初愿景。

## MVP 阶段的退出标准

MVP 阶段的退出条件，是获得真正的产品-市场匹配证据：证明一个具体、可识别的用户群体已经认为产品足够有价值，愿意回来使用它（留存）、为它付费（收入），或把它推荐给别人（推荐）。

## MVP 阶段的挑战

在 MVP 阶段，创始人的首要指令是速度和判断力。这里的挑战集中在：你能否足够快地构建正确的东西，并以正确的方式构建，同时不走那些以后会让你付出代价的捷径。

### 智能体技术债

**挑战：** 因为 AI 实际上移除了过去控制哪些东西能进入生产环境的所有自然瓶颈，速度已经是必然。但如果创始人在 MVP 构建中只考虑速度这一个变量，就可能积累自己难以偿还的技术债。

在 MVP 阶段，一定程度的技术债是合理的，前提是你理解它必须在规模化之前得到管理。普通技术债会逐渐累积，可以随着时间或在专门的冲刺中清理。但 AI 技术债会复利增长。

如果没有把规格和架构约束写在 AI 能读到的地方，每个会话都会从零开始重新推导基础决策，而这些决策会发生漂移。最后你会得到一个背后没有连贯心智模型的代码库。问题不在于某一个部件一定很差，而在于这些部件从未被设计成能够相互配合。这是真正的问题，而且它确实往往很晚才浮出水面。

### 误信虚假的产品-市场匹配

**挑战：** AI 工具可以生成令人印象深刻的早期数字，但这些数字并不能保证市场需要你的产品。

早期势头，是创始人能经历的最强心理体验之一。经过数周或数月的验证工作和谨慎、有纪律的构建之后，发布一个产品会让人感觉自己一直都是对的。

智能体式编程工具可以帮助你比以往任何时候都更快到达这个时刻。但早期牵引并不等于产品-市场匹配。发布时的热度常常来自短暂力量，例如创始人的朋友、投资人其他被投公司的潜在买家，或者 Hacker News 上一个带来流量峰值的标题。遗憾的是，这些都无法可靠预测第 6 周或第 12 周会发生什么，尤其是在最初的助推消退之后。

### 零摩擦范围蔓延

**挑战：** 当构建感觉毫不费力且近乎免费时，总会还有一个很酷的功能可以加，或者还有一个边界情况可以处理。这种范围蔓延可能弊大于利。

范围蔓延一直是创业风险。现在的区别在于，过去抑制它的传统约束，也就是真实的工程时间成本，在一个功能只需要一个下午而不是一个冲刺就能加上的情况下，已经不再以同样方式存在。

这里的挑战是，每一个单独的新增项看起来都站得住脚。产品当然应该处理那个边界情况；用户当然会想要那条工作流。由于用智能体式编程构建每一项都只需要很少努力，它们在当下并不会显得像范围蔓延。但随着产品越过最初边界不断膨胀，你会冒着失去方向和动量的风险。

解药是在开始构建之前写下一份范围定义，说明产品做什么，刻意不做什么，以及来自真实用户的哪些具体证据可以证明现在值得添加新东西。这样，决策点就从“我们要不要做这个？”转变为“是否已经有足够关键数量的用户告诉我们，如果没有这个，他们无法从产品中获得价值？”

### 因经验不足而不安全

**挑战：** 创始人如果在尚未理解基本安全原则之前，就用 AI 工具匆忙把应用推向市场，最终会让用户暴露在本可避免的风险中。

一个艰难事实是：智能体式编程工具会生成能工作的代码，但不会天然生成安全的代码。功能性代码很容易判断，因为功能要么可用，要么不可用。安全漏洞在被利用之前是不可见的，这意味着没有自然反馈回路提醒第一次创业的创始人出了问题。然而，把一个真实 MVP 发给真实用户，意味着真实数据、真实暴露面，以及一旦出事就会有真实后果。

忽视安全并不是 AI 原生项目才有的新问题。每个时代的自举型创业公司都经常把安全考虑推迟到构建后期，有时甚至等到生产发布前夕。任何用户接触你的应用或解决方案之前进行安全审查，是把一个最小可行产品发布到世界上的最低责任门槛。

## Claude 如何帮助 MVP 阶段的创始人

### 在构建前定义架构

在 Claude Code 写下第一行生产代码之前，先用 Claude 定义并记录那些将支配本阶段所有构建工作的架构决策：要遵循的模式、要避免的依赖、正在做出的取舍以及原因。这份输出会成为聚焦的架构上下文文档，并确立 Claude Code 运作时的护栏。

如果没有这些上下文，每个会话都会从零开始，Claude Code 被迫推断自己的结构性假设。让 Claude Code 在没有护栏的情况下构建，会产出功能可用但结构不连贯的代码库；而在不连贯的代码库上迭代和扩展，最终是在浪费时间和 token。迟早会到达一个临界点，代码不可避免地坍塌，迫使你从头重建。

- **练习：** 在打开 Claude Code 之前，先打开 Claude 并描述你要构建的东西：它解决的核心问题、服务的用户，以及你现实预期未来六个月会达到的规模。请它帮助你定义应当支配 MVP 构建的架构原则、在你的约束下应避免的依赖，以及你在这一阶段有意识接受的取舍。

接下来，把这些输出保存为 CLAUDE.md Markdown 文件。这就是你的架构上下文文档：构建工作的第一个产物，也是之后每个会话都会依赖的产物。CLAUDE.md 文件是 Claude Code 的项目级指令，为项目提供特定上下文和说明；当 Agent SDK 在某个目录下运行时，它会自动读取这些内容。从功能上说，它们就是项目的持久“记忆”。

### 定义并执行 MVP 范围

没有摩擦的范围蔓延，是 AI 时代 MVP 最典型的失败模式之一。正如你需要定义并记录产品应用的架构，你也需要在构建任何单一功能之前，定义 MVP 的范围。

Claude 可以帮助你创建一份范围文档，说明你的 MVP 产品做什么、刻意不做什么，以及功能修订标准：在此时此刻，来自真实用户的哪些具体证据可以证明值得新增某项内容。

当新功能想法出现时，而且它们一定会出现，你可以用 Claude 压力测试：这究竟是来自用户的真实信号，还是披着产品思考外衣的创始人热情。

### 用 Claude Code 构建 MVP

一旦架构和范围被定义好，Claude Code 就成为主要的 MVP 构建工具。用它生成、测试、调试并迭代你的代码库，但要把每个会话都视为对已做产品决策的执行，而不是顺手塞进新决策的机会。

每次 Claude Code 会话开始时，都要（1）重新查看你的范围文档，（2）向模型提供 CLAUDE.md 架构上下文文档。每次会话结束时，用本次会话暴露出的任何决策更新它。目标是得到一个你能够解释其结构的代码库，而不只是一个能跑的代码库。

- **练习：** 为 Claude Code 工作创建一个简单的会话模板，其中包括架构上下文文档、本次会话的具体任务，以及需要遵守的约束或模式。每次会话结束时，在上下文文档中添加一条简短日志，说明构建了什么、做出了什么决策，以及本次会话引入了哪些假设。每次花五分钟做文档，是防止架构漂移复利成不可管理代码库的廉价保险。

### 任何用户接触之前进行安全审查

作为 AI 原生创业公司的创始人，你有责任知道代码库里有什么，理解任何潜在暴露路径，并且不要把明显漏洞交付给信任你数据的真实用户。

Claude 可以对 AI 生成的代码做有用的第一轮安全审查，并帮助识别常见漏洞。这是发布前值得纳入循环的好习惯。但它不能替代安全工具；在风险更高的场景中，也不能替代人类审查者。把它当成替代品的创始人，往往会成为安全事故故事里的主角。

Claude Code Security 更进一步：它会扫描代码库中的安全漏洞，并提出供人类审查的定向补丁，暴露出传统方法可能漏掉的问题。

> 注：在本电子书发布时，Claude Code Security 仍处于有限 beta 阶段。因此，在把它纳入你的工作流之前，请检查当前可用性。

- **练习：** 在部署给任何真实用户之前，用一个明确 brief 让 Claude 审查你的核心应用代码：检查认证和会话处理、API 响应中的数据暴露、输入校验和注入风险，以及存在已知漏洞的依赖。认真对待每一项发现，并评估是否需要修复。凡是涉及认证、密钥或数据处理的内容，都应有人类审查。

### 在发布前建立度量框架

那些把早期牵引误认为产品-市场匹配的创始人，通常也是发布后才开始追踪数据的人。他们选择指标是为了评估哪些东西有效，而不是为了暴露哪些东西无效。解药是在第一个用户出现之前，就建立度量框架。

用 Claude 定义哪些指标对你的具体产品重要，基准是什么，以及数据中的哪些模式可以构成真正的产品-市场匹配，哪些只是好看的噪音。具体来说，在发布 MVP 之前，就设定留存基准、激活标准，以及第 7 天和第 30 天目标。

接下来，为你的具体产品定义什么叫假阳性：例如，有注册但没有激活，有收入但没有留存，或者一开始很兴奋但没有重复使用。当数据到来时，让 Claude 针对你的牵引表现提出反方论证：一个怀疑者会如何解释这些数字？

### 管理发现和用户反馈的运营工作

一旦真实用户进入产品，运营层面的工作会迅速扩张。Claude Cowork 可以处理那些重要但繁琐的工作，例如建立和维护用户联系人名单、运行触达序列、安排反馈会议、分流 bug 报告，以及跟踪迭代周期。想法阶段用于管理发现工作的同一套 MCP 集成，在这里同样适用。

对于用户反馈中需要细腻探索的部分，仍然要让人参与收集循环。例如，用户说“这个很好，但我希望它也能……”，这需要解释：这是核心需求，还是锦上添花？它是这个客户特有的，还是代表某个细分人群？缺失的功能才是真问题，还是上游的 onboarding 出了问题？没有工具能替你回答这些问题。

- **练习：** 配置 Claude Cowork 来运行你的 MVP 阶段反馈循环：向早期用户名单起草触达内容，安排反馈会议，为 bug 报告和功能请求设计结构化收集流程，并每周写一份汇总。先由你自己审阅汇总；之后，你可以让 Claude 分析这些信息，捕捉你可能遗漏的重要点。

### 朝证据迭代，而不是朝完整度迭代

MVP 阶段结束的标志，是你拥有真正的产品-市场匹配证据，不管产品感觉上是否“完成”。宣布你已经实现产品-市场匹配、准备从 MVP 阶段进入发布阶段，本质上是一项判断练习，需要把创始人的直觉和已收集证据结合起来。不过，也有一些有用的试金石：

- **Sean Ellis 测试：** 问你的活跃用户：“如果你不能再使用这个产品，你会有什么感受？”如果超过 40% 的人回答“非常失望”，这是一个有意义的 PMF 指标。
- **努力程度测试：** 在产品-市场匹配之前，留存需要持续干预，包括频繁触达、激励、个人跟进，以及创始人投入大量近乎英雄式的精力来维持用户参与。产品-市场匹配之后，产品开始自己完成这项工作。当事情开始从“推”变成“拉”，这种努力方向的变化，就是某种真实改变已经发生的最清晰信号之一。

归根结底，没有任何单一数据点能够确认产品-市场匹配。它必须是在多个迭代周期中持续成立的一种模式，你才能真正说它已经发生。

### 当证据要求时就转向

如果你投入了所有这些工作，却仍然无法实现产品-市场匹配，该怎么办？你的结果没有确认最初的方向，并不代表失败，而是系统正在正常工作：MVP 阶段的设计目的，就是在你对错误答案过度投入之前，把这些信息暴露出来。

当数据不支持当前产品时，用 Claude 一起梳理这些数据到底在告诉你什么。

- **探索替代客户细分。** 也许那些没有转化的用户，从一开始就不是正确目标。很多时候，正确受众已经存在于你的数据中，只是权重被低估了。
- **调整产品价值主张。** 也许你的受众是正确的，但 MVP 没有真正引起用户共鸣。调整 onboarding、信息表达或核心功能强调，有可能在不改变已构建内容的情况下解决这个问题。

同时，也要对一种可能性保持开放：断裂可能足够深，需要更根本的改变。

- **练习：** 如果你已经完成三轮或更多迭代周期，却没有朝产品-市场匹配基准取得有意义的进展，就先用 Claude 做一次诊断，再决定下一步。把你的留存数据、用户反馈和最初的问题假设交给它，并问三个问题：

  - 这些数据中，是否有某个细分人群的反应不同于其他人？
  - 设计价值和体验价值之间的缺口，是定位问题，还是产品问题？
  - 如果当前产品要找到真正的 PMF，哪些事情必须为真？根据你现在看到的情况，这种场景现实吗？

让答案决定你是调整、转向，还是回到想法阶段。

# 第 5 章：发布阶段

如果说 MVP 阶段是在证明你的产品值得存在，那么发布阶段就是在证明你的业务值得增长。

## 发布阶段目标

在发布阶段，创业者必须把早期牵引力转化为可重复、可持续的增长引擎。除了让产品具备生产可用性，你还必须加固底层基础设施，同时围绕产品真正搭起一家公司。

在想法阶段和 MVP 阶段，创业公司天然会以创始人为中心，因为你需要完整的现场感和紧密的反馈回路。但到了现在，如果创始人仍试图亲自抓住每一条线索，就会变成发布阶段的瓶颈。目标不是把你自己从公司里拿掉，而是建立一套运营系统，把你的注意力释放出来，留给那些只有创始人才能做的判断。

## 发布阶段退出标准

发布阶段的退出条件包含三个要素：

1. 增长是可重复的，并且由渠道驱动。你不只是留住用户，还能通过明确渠道可预测地获得用户，并理解背后的单位经济模型：CAC、LTV 和回本周期，都是你知道且能讲清楚的数字。
2. 产品能够承载生产负载。基础设施已经加固，安全与合规安排到位，并且在真实生产条件下保持可靠，而不只是能通过你测试过的场景。
3. 运营不再卡在创始人身上。流程已经存在，自动化已经落地。你不再是那个亲自处理支持、分诊、冲刺规划或报告的人。

## 发布阶段挑战

找到产品-市场匹配，是早期创业生命周期里最难的问题。现在，创始人的挑战变成了守住它。发布阶段正是这样一个地方：公司已经找到了真实的产品牵引力，却仍可能因为围绕产品、支撑产品的组织跟不上而散掉。下面是需要警惕的失败模式。

### 技术债开始到期

挑战：为了速度和验证而搭出的 MVP 代码库，足以证明产品能跑起来；但生产流量、新功能和不断增长的复杂度，正在暴露当初留下的捷径。

在 MVP 阶段，积累一些技术债是为速度付出的合理代价。到了发布阶段，这些债务开始产生利息，而且拖得越久，修复成本就越高。

解决办法是做一次系统性的架构审计，找出结构性薄弱点；对最严重的问题进行有针对性的重构；并显著扩展测试覆盖率，避免下一轮功能开发又把同样的问题带回来。

### 创始人成为瓶颈

挑战：在 MVP 阶段，创始人参与每一个环节是一种优势。到了发布阶段，支持请求变多、产品决策堆积、运营复杂度成倍上升，同样的本能就会变成约束。

从“亲自做事”转向“设计能做事的系统”，是创业生命周期里最困难的转变之一。因为它很少有一个清晰发生的时刻，所以真正的风险是完全错过这次转变：你还停留在建设者模式里，而组织已经在你周围停滞。明显的信号包括：本该一小时完成的决策，现在要等你一周才轮到；支持请求越积越多，因为只有你知道答案；运营任务只有在你本人想起来时才会发生。

补救办法是彻底审视所有仍由你亲自处理的事情，从最小的任务到风险最高的决策都包括在内，然后判断哪些可以系统化，哪些可以委派，哪些确实仍值得创始人投入时间和注意力。

### 安全与合规不能再往后推

挑战：在 MVP 阶段，保持安全与合规措施简单是可以接受的；但现在有了真实用户、真实数据，并且可能开始面对企业合同，这就会变成风险。

在 MVP 阶段，如果只有少量测试用户，生产环境里也没有敏感数据，安全漏洞更多是理论风险。但一旦产品进入生产环境，有真实用户依赖它，那个“假设中的问题”就会变成非常现实的暴露风险。与此同时，原型阶段不适用的合规要求，一旦你开始处理客户数据、处理付款，或面向受监管行业销售，就一定会适用。

补救办法是在生产规模到来之前，而不是之后，做一次系统性的安全与合规审查；并把所有暴露出来的问题都视为下一波用户到来前必须完成的整改，而不是建议项。

### 还没准备好就扩张

挑战：新市场和融资机会看起来像增长机会。但它们也可能是产品-市场匹配消失的地方。

你已经建立起来的初始牵引力是真实的，但它也特定于你的早期受众。过早进入一个与原始市场明显不同的市场，会带来新的用户行为、合规要求、支付基础设施和基线预期，而你的产品并不是围绕这些东西设计的。突然之间，新变量太多，你会失去清晰解读自身数据的能力。你还会冒着忽视原有用户群的风险，去追逐一个尚未被验证的新受众。

## Claude 如何帮助发布阶段的创始人

在发布阶段，Claude 的三种形态都会被充分使用，而且它们会彼此支撑：每个工具产生的输出，都会成为另外两个工具的输入。结果会自然复利；创始人把三者一起使用时，得到的东西会超过单个工具效果的简单相加。

这正是超精简创业模型在结构上成为可能的原因。当 Claude Code 构建产品，Claude Cowork 构建产品周围的公司，而 Claude 帮助把产品知识和组织知识运营化时，一个小团队就能像规模大数倍的公司一样运转。

### 在技术债复利之前修复它

你的 MVP 代码库能工作，但它也需要一次系统性的修复扫描，找出任何可能变成结构性负担的技术债。

首先，用 Claude Code 做一次完整的架构审计：识别代码库哪里脆弱，哪些捷径会变得昂贵且难以维护，以及哪些地方的测试覆盖薄到下一轮功能开发很可能重新引入同样的问题。

把 Claude Code 的审计发现再交给 Claude，让它帮助分诊并排序修复工作：哪些必须在下一次发布前修掉，哪些可以等一个冲刺，哪些在当前阶段属于可以接受的持续债务。

这也是记录 MVP 阶段架构决策的时刻：那些当时因为没时间写下来、只存在你脑子里的决策。现在把它们写进 `CLAUDE.md`，可以确保未来每一次 Claude Code 会话都从同一个理解出发：系统是如何设计的，以及为什么这样设计。

- 练习：让 Claude Code 审计你的 MVP 代码库，并产出一份按优先级排列的清单，列出结构性弱点、测试覆盖缺口和重构候选项。然后把这份清单交给 Claude，请它把修复工作拆到接下来几个冲刺里：哪些重大问题必须先解决，哪些可以和功能开发并行处理，哪些可以等待。

### 建立能够替代创始人注意力的系统

要建立一套运营系统，把你的注意力释放出来去处理只有创始人能处理的职责，前提是你必须准确知道自己的注意力流向哪里。用 Claude Cowork 对当前运营负载做一次结构化审计：记录每一项重复任务、每一个落到你桌上的决策，以及每一条只有因为你亲自记得才会发生的工作流。然后让 Claude Cowork 把这份清单分类：哪些可以完全自动化，哪些需要人但不一定需要你，哪些确实需要创始人判断。

审计完成后，用 Claude Cowork 设计自动化候选项的工作流逻辑：每条工作流由什么触发，决策规则是什么，输出长什么样，完成后流向哪里。

### 把安全与合规变成产品工作流

用 Claude Code 找出在 SOC 2、GDPR、HIPAA 审计中经常出现的代码层问题，以及目标市场所要求的标准。这会同时暴露漏洞和合规缺口。把这些发现交给 Claude，帮助你确定修复优先级，并设计企业买家在签约前会要求看到的控制措施、审计日志和访问管理。注意：AI 扫描是辅助工具，但不能替代合格的合规审查。

接下来，把合规工作流纳入开发周期，而不是把它当成一次性项目；合规文档需要持续维护和更新。对于正在接近企业合同或国际市场的创始人来说，这也是用 Claude Code 安全扫描为独立安全评估做准备的时刻。

- 练习：让 Claude Code 做一次代码层安全审查，并按目标市场需要的框架来组织。把输出交给 Claude，请它产出两样东西：一份按优先级排列的安全整改顺序，以及一份文档和控制措施清单，用来满足潜在企业买家的合规审查。

### 搭起你一直跳过的产品管理流程

发布阶段需要一组轻量、可重复的流程，它们能够在没有创始人介入触发或推动的情况下运转。用 Claude 设计你的产品时间线和工作周期如何组织，一个规格说明在 Claude Code 开始写功能前必须包含什么，Bug 报告如何分诊和流转，以及每周指标报告覆盖什么、如何分发。

流程设计完成后，用 Claude Cowork 构建并运行运营层：安排冲刺仪式，把进入的 Bug 报告路由到正确位置，从已连接的数据源汇总每周指标，并维护让用户信号持续流入产品决策的反馈回路。

- 练习：请 Claude 设计一套轻量级产品管理操作系统：明确的冲刺节奏、最小规格说明模板、Bug 分诊决策树，以及一份从真实数据源拉取信息的每周指标简报。然后设置 Claude Cowork，让它实施并运行这套系统里的周期性运营元素，比如排期、路由和报告汇总，使这些事情按时发生，而不需要你。

# 第 6 章：规模化阶段

在规模化阶段，创始人的角色会从建设者重新转向面向公众的高管。产品仍然是核心，但你每天亲自处理的工作会越来越多地转向公司本身。你的注意力必须扩展到规模化阶段的新活动，比如分析师简报和 IPO 路演；同时，你仍要努力保持那种精简、以 AI 为中心的结构性优势。

## 规模化阶段目标

扩展技术基础设施的工作会继续进行，而现在还要叠加扩展组织本身、让组织成熟为一家业务公司的工作。

到了规模化阶段，你面对的是从数千用户走向数百万用户，从一个市场走向多个市场。在之前每个阶段，增长都还可以靠贴近用户、基于紧密反馈回路的数据和足够多的创始人直觉来摸索。现在，目标变成了建立由成熟组织运营支撑的系统性增长。

对于 AI 原生创业公司来说，你的目标应该是通过累积深度建立可防守的护城河。这种深度来自你嵌入产品中的专业知识，来自产品与你的用户所依赖的其他工具和平台之间的集成深度，也来自专有的系统数据和工作流。那些一直沿着同一个方向、在一致基础设施上持续构建的创始人，现在拥有了真正难以复制的东西。

在这个阶段，公开市场投资者、分析师、监管者、企业采购团队和潜在收购方都会带来更大的压力，也会带来更强的怀疑，因为现在赌注更高了。你的产品和组织必须经得起外部审视：不只是你已经构建出来的能力，还包括围绕这些能力的治理、合规姿态、财务控制和战略叙事。

## 规模化阶段退出标准

规模化阶段的退出条件不再是某一个单点里程碑，而是一个阈值事件：即使创始人越来越少直接管理日常运营，公司也能持续运转。你已经证明了系统性增长；建立了能满足最苛刻外部审查者的组织治理与合规基础设施；并且能有力回答这个问题：“如果一个资金充足的既有巨头今天复制你的产品，你的用户还会留下来吗？”

在实践中，这个阈值通常会以三种形式之一出现：达到不再需要外部资本的规模化可持续盈利，具备 IPO 准备度，或被收购。三者都要求你的增长是系统性的、可审计的；你的产品护城河经得起审视；你的组织在运营上成熟且可持续。

当这些都成立时，就值得说一声恭喜：你的创业公司已经从一个赌注，变成了一门生意。

## 规模化阶段挑战

### 委派运营层

挑战：规模化阶段的运营系统必须可靠、可持续地运行，不能还需要人盯着。对于从第一天起就亲力亲为的创始人来说，这个转变既是结构性挑战，也同样是心理挑战。

你在发布阶段做的是创建系统；到了规模化阶段，任务变成了两件事：第一，让这些系统成熟到完全值得信任；第二，真正信任它们。

这比听起来更难。即使你是一个擅长委派的创始人，也并不总能清楚知道该交出去什么、该留在自己手里什么。交得太多、太快，尤其是交给 AI 自动化系统，关键决策就可能在缺少只有创始人才能提供的关键上下文时被做出。但抓得太久，你又会变成瓶颈。

这里的根本挑战，是识别那些只存在于创始人脑中或未记录工作流里的组织知识，然后把它编码进有文档、可审计、可转移的系统中。

### 扩展技术运营

挑战：客户不再只评估你的产品；他们还想知道你的组织是否能成为可靠的基础设施伙伴。

前三个创业阶段的技术挑战主要围绕代码库：在不积累技术债的情况下构建正确方案，然后为真实用户加固安全与合规。进入规模化阶段之后，挑战变成了代码库周围的一切：创建支持基础设施、文档和可靠性保证，用这些东西传递成熟度。

大型客户和机构买家在签署多年合同之前会要求看到这些东西；签约之后，他们也会按这些标准要求你。

不过，把你带到今天的同一套 AI 基础设施，也能帮助你建立专门的支持职能：有明确响应时间，有新客户工程团队真正能用的文档。

### 扩展组织职能

挑战：一家规模化阶段的公司通常需要招聘、薪资、会计、法务运营等组织基础设施，不管实际有多少人在运转它。

在发布阶段，系统化运营意味着自动化那些消耗创始人注意力的工作流。到了规模化阶段，创业公司现在需要发展出一组更广、某种程度上也更关键的运营职能，例如财务报告、合规监控、合同管理和客户支持，等等。

### 建立 GTM 职能

挑战：自然增长有天花板，而大多数规模化阶段的创始人会在真正建立 go-to-market 职能之前就撞上它。

创意、MVP 和发布阶段的增长，往往来自创始人主导的销售：可能是一篇时机刚好的 Product Hunt 帖子，也可能是与早期客户的个人关系。但这种自然增长只能走到某个点，大多数创业公司会在规模化阶段碰到这个上限。迹象包括用户曲线变平、获客成本上升，以及销售管线只有在创始人亲自参与时才会推进。

规模化阶段的增长，需要建立一个专门的增长引擎，让你的产品触达新的、更广泛的受众。不过，大多数创业创始人大概从未真正运行过营销、销售、分析师关系这类项目。一个正经的 GTM 动作不只是建立新的系统和流程，还包括创造品牌声音和产品故事，明确你想如何谈论自己的产品。因为到了创业生命周期的这个阶段，你需要的不只是触达单个新用户，还要触达投资者、企业买家这样的完整目标受众。

幸运的是，GTM 职能不必很大才有效；构建产品的同一套 AI 基础设施，也可以帮助你从零启动产品走向市场的过程。

## Claude 如何帮助规模化阶段的创始人

在早期创业阶段，Claude 是产品本身的基础设施：它是验证创意的研究伙伴，是设计并构建原型的工程团队，也是让单创始人创业成为可能的 AI 运营层。到达规模化阶段的 AI 原生创业者，现在可以继续用 Claude、Claude Code 和 Claude Cowork，以他们当初构建公司的方式继续扩展公司。

### 把日常任务交给 Claude Cowork

进入规模化阶段时，先清醒地看清你现在最需要把时间和注意力投入在哪里。对于从未建立过一家公司的首次创业者来说，这可能并不容易。Claude 可以帮助你列出在这个阶段只有你应该做的事情，比如产品叙事决策、董事会关系、企业级交易，以及创始人与创始人之间的对话。凡是不在这张清单上的事项，都是委派或交给 Claude Cowork 自动化的候选项。

- 练习：用 Claude 为你当前的运营层制作一张瓶颈地图：所有目前经过你的工作流、决策和审批。然后请 Claude 推演：如果你一周不可用，每一项会发生什么。那些停滞的工作流，就是你仍然亲自参与到足以拖慢进展的地方。

这些内容与你之前用 Claude 梳理出的创始人优先事项和责任清单如何对应？

接下来，就该压力测试你已经建立的系统，看看它们是否真的准备好随着业务增长一起扩展。

- 练习：用 Claude 梳理你当前的工作流，然后请它分析：如果你一周不可用，每一项会发生什么。那些停滞的工作流，就是交接标准、升级路径或异常处理仍需收紧的地方。Claude 可以帮助分析失败点，并建议合适的修复方式，让你按需更新或替换 Claude Cowork 自动化。

### 将技术运营扩展为企业级基础设施

随着规模扩大，买家需要确信你的产品和组织值得作为长期基础设施来信任。代码库内部的技术工作当然仍会继续，但现在，代码库周围也有技术工作需要处理。

第一步是把组织知识转化为可扩展的系统。用 Claude 起草并维护企业采购预期会看到的书面基础设施，包括产品文档、支持手册和 SLA。

与此同时，让 Claude Code 按照企业合同要求的具体可靠性和安全标准审计并加固代码库，并补齐 Discord 社群式支持从来不必提供的技术支持基础设施：日志、监控、事故响应工具，以及让 SLA 真正可执行的可观测性层。

随后，Claude Cowork 运行企业支持本身的运营层：工单路由、升级工作流、由产品变更触发的文档更新、续约跟踪，以及企业客户成功所依赖的报告节奏。三者结合起来，可以让一个小团队呈现出大型组织的支持姿态，而这正是签下多年企业合同前你必须证明的东西。

- 练习：挑出三个最苛刻的潜在客户，或确定三个你很想签下的理想客户。请 Claude 做一份差距分析：这些客户的企业采购团队在签署多年合同前，会期待看到哪些文档、SLA 和支持基础设施？你现在还差在哪里？用输出结果在 Claude Code 和 Claude Cowork 之间安排技术与文档工作的顺序。

### 建立真正的 GTM 职能

创始人的拼劲把你带到了这里，但要扩展创业公司，你需要创建并执行真正的 go-to-market 战略。AI 可以帮助你构建，然后运行这整套 GTM 引擎。

Claude 可以从零开始帮助搭建基础 GTM 资源：市场细分、信息架构、分析师关系策略、销售手册，以及当你开始面对公开市场投资者、企业买家和华尔街分析师时真正重要的投资者指标叙事。每类受众都有自己的词汇，也会按自己的标准评估你；Claude 的工作，是把你产品的价值主张翻译成适合每个受众细分的产品营销方法。

现在，Claude Cowork 可以成为你的战术执行层：内容管线、外联序列、分析师简报的后勤安排、新闻与公关节奏、CRM 卫生、销售管线报告，以及许多把 GTM 战略转化为实际商业动作的周期性循环。

当 GTM 动作需要产品营销基础设施时，比如交互式演示环境、集成文档、沙盒租户、API 参考、技术一页纸，Claude Code 可以为你构建。买家会期待从技术上评估你的产品；在规模化阶段，一个 Loom 视频和一份销售幻灯片已经不够了。这也是让你的 GTM 动作异步运行的基础设施：一个做得好的演示环境，可以在你参加董事会会议时帮你推进交易。

### 把领域专业知识和组织知识转化为 AI 上下文

许多超精简创业创始人，正在为某个真实世界问题构建高度具体的应用或工具，而这个问题通常来自他们在某个行业里的亲身经历或一线观察。智能体式 AI 现在让从未写过一行代码的创始人，也能用自己的领域专业知识构建解决复杂问题的产品。Claude、Claude Code 和 Claude Cowork 分别参与其中，把创始人知识转化为不断复利的产品具体性。

用 Claude 捕捉、组织并打磨创始人知识，就是把领域专业知识放到产品能够触及的位置。通过长对话、项目和记忆，创始人可以把自己知道的一切都分享出来：行业黑话、监管陷阱、边缘案例、挫败感、为什么这个问题显而易见的答案行不通。这些内容会进入结构化、可搜索的上下文。Skills 随后可以把重复出现的工作流，比如“我如何审计一份商业租约”“我如何分诊一份患者 intake 表”，编码成 Claude 每次都以同样方式运行的可复用例程。几个月后，这会变成一层专有知识基底，任何通用 AI 都难以匹敌。

用 Claude 外化你的领域知识，对于把行业特定边缘案例编码进产品非常有价值。比如，一个通用 AI 医疗账单工具可能会在 340B 药品项目理赔上失效，而你的产品有针对它们的具体逻辑。Claude Code 帮助你把同行专业人士常见的挫败点，转化为校验逻辑、提示词优化，或与某个竞争对手没听说过的小众行业系统之间的 MCP 集成。结果是，你的应用或工具在深度和广度上都会持续复利，而竞争对手根本难以复制。

- 练习：找出一个通用竞争对手在你所在垂直领域里一定会做错的边缘案例。和 Claude Code 一起，基于你真实见过的场景，为它构建一个专门测试用例，不是单元测试。每当类似边缘案例出现，就把它加进去。你的测试套件会变成一张护城河地图。

### 将累积的用户数据复利成可防守优势

当用户与你的产品互动时，他们会产生行为信号，也就是他们接受哪些输出、拒绝哪些输出。这些信号会反过来影响产品路线图。随着时间推移，你会理解自己特定用户群体的具体模式、偏好和边缘案例。所谓复利价值，就是这个意思：每一次改进都会让产品更有用，进而带来更多使用，更多使用创造更多反馈，更多反馈又推动更多改进。

这些数据是被时间锁定的、上下文特定的，而且复制者不可能重建：你无法直接买到数千名用户在你的产品里不断打磨自己工作流后留下的行为指纹。

Claude 可以帮助审计你已经收集的用户交互数据，找出其中信号最高的行为模式，并设计把持续使用转化为系统性模型改进的反馈回路。

- 练习：把你的产品交互数据摘要交给 Claude：你一直在收集什么，收集了多久，以及你知道用户如何随着时间与你的产品互动。请它识别这些数据中信号最高的三种行为模式，并为每一种设计一个反馈回路，把它转化为系统性模型改进。然后请它帮助你起草一页护城河叙事，用于产品营销：你的数据飞轮如何运转，已经转了多久，以及为什么一个资源充足、今天才开始的竞争对手无法在两年内复制它。

### 创造工作流锁定

复利的数据网络效应让你的产品更难被复制，而用户工作流锁定让你的产品更难被离开。用户在日常运营中使用你的产品越久，它就越深地嵌入他们真正工作的方式里。他们在它之上建立了自动化，培训了人员使用它，并把它连接到自己的数据源和其他工具。他们开发的提示词、打磨的工作流、标准化的输出，都已经围绕你的产品做什么、如何做而成形。到了这个点，切换不再是一个产品决策，而会变成一个完整的运营项目。

创造工作流锁定的第一步，是请 Claude 按集成深度绘制你当前客户群的地图。对每个客户细分，识别他们在你的产品之上建立了哪些工作流，以及他们依赖哪些集成。这会显示你的产品在哪里真正黏住了客户，以及哪里还需要更深。

你提供的集成越多，客户就有越多空间构建依赖你产品的工作流。Claude Code 可以帮助你快速搭起与目标用户依赖的数据管线、项目管理工具和其他系统之间的原生集成。Claude Code 也可以构建 API、webhook 和 SDK，让客户不只是使用你的产品，而是在它之上继续构建。这是最深层的锁定。

- 练习：请 Claude 帮你为前十名客户做一次工作流集成审计。对每个客户，记录他们建立的自动化、依赖的集成、经过你产品的团队工作流，以及你对其切换成本的估计。然后请 Claude 识别这组客户中的模式：对你的具体产品来说，哪些类型的集成会创造最深的锁定？你可以构建或开放什么，来加深那些目前还停留在表层的客户集成？

# 第 7 章：同一份工作，新的规则

在 AI 时代，创始人的工作并没有改变：找到一个真实问题，构建能解决它的东西，并把它扩展成一家重要的公司。改变的是到达那里的路径。贯穿创意、MVP、发布和规模化这四个阶段，AI 把原本以季度计的事情压缩成了以周计。

过去需要几个月的验证循环，现在一个下午就能完成。一个可运行的原型不再需要一个技术栈正好匹配的联合创始人；它需要的是一个清晰的问题，以及和编码智能体进行几次聚焦会话。发布准备从上线前的混乱冲刺，压缩成一个持续的工作流。到了规模化阶段，过去会迫使早期员工陷入救火角色的运营重量，也越来越可以交给 AI，让团队把注意力放在那些会成为护城河的判断题上。

瓶颈不再是你能构建什么，而是你选择构建什么。
